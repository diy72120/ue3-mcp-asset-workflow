# 从参考图到可发布新地图

用于文字/图片描述驱动的从零地编。它补充已有地图迁移流程，不替代当前 MCP Schema，也不保存具体地图配方。发布阶段接着读 [地图制作与发布](map-publication.md)。

## 1. 先拆空间结构，再查资产

把描述分成可验证的结构：主体轮廓、中心与分支关系、层级高差、通行路线、边缘防护、背景/动效及主要图案。先确定哪些靠几何表达、哪些靠材质表达，不把图片上看似相同的颜色当作相同模型。

- 资产库优先筛轮廓、尺寸、构件角色及搭配线索；完整原生对象路径才是放置身份。已分类和未分类资产均可作为候选，未分类候选仍需观察核实，不先重建或标完全库。
- 优先使用现有模型、已有装配关系和真实参考关卡；没有完全匹配的模型时选结构合适的，贴图只能改变表面，不能补出缺失楼梯、实体厚度或碰撞。
- 缩略图用于筛选，不证明实际朝向、地面承载、拼接精度和场景受光。进入当前地图核对真实实例；文字标签辅助选材，不保证自动布局正确。
- 用户允许本地 Bridge 就用本地 MCP；明确要求 HTTP-only 时保持纯 MCP 边界。图库分类任务的远端限制不能误推广为所有地编任务都必须用 HTTP。

先搭可读的主体和高差，再扩充细节。先完成一个模块并确认朝向、比例和拼接，再按已确认的关系复制；避免把单个模块错误放大成整圈。

## 2. 保存与材质变体隔离

新建地图使用独立编辑源、独立自定义资产包及独立发布目录。复用原库网格并不授权修改原材质、碰撞或粒子模板；需要改外观时复制必要资源并检查内部引用。地图另存并不会自动隔离外部资源。

图片模型生成贴图时：

- 提示词描述实际 UV 使用方式、图案边界、透明度和需要保留的主体；生成图、材质绑定和映射连续性分别验收。
- 检查像素尺寸、通道和 UE3 当前导入限制。图片模型不一定遵守指定尺寸；尺寸适配需按用户授权，保留原图。某个导入接口拒绝大图、接受小图不证明整个 UE3 只支持该尺寸。
- 尺寸转换不是重新创作图案，不能私自改色、裁切或改变已批准构图。涉及多块拼图、重复 UV 或拉伸时查贴图映射参考，不能靠加大图片掩盖 UV 问题。
- 贴图覆盖片与实际承重模型分开；覆盖片可不参与碰撞/导航，以免出现重复表面或干扰可走区。

## 3. 视觉结构和可走结构双重检查

- 模型看起来像地板，不代表有 BodySetup 或可用碰撞。BlockAll 只改变响应，不生成缺失碰撞几何。优先使用已有可靠碰撞的承重网格，装饰仍按装饰处理。
- 导航角色按地面、障碍和纯视觉区分。项目 PATH 图层及碰撞设置需回读；保留无关原图层，不用重设所有碰撞来代替确认职责。
- 楼梯上下接点、平台接缝及不同高度之间分别检查。导航文件存在并不证明通路连通；边缘栏杆看似完整也不保证能阻挡角色。
- 护栏按可走面的外轮廓逐段检查，包括转角、分支平台外侧和楼梯接点。顶视核对连续性，透视核对高差和悬空；截图看不见的区域不能直接算已补齐。
- 镜头远近、G 显示及有光照/无光照模式分别服务于结构和最终外观验收。动态云雾或粒子观察需要实时播放；静态截图不证明运动。
- 背景和动效不应遮掉主要通路。材质、粒子、灯光分别归因，不能用共享全局雾修改来补一个局部效果。

## 4. 空白地图缺少的发布前置

旧图可能已有地图信息、区域范围、Pylon、图层和灯光范围，空白图必须显式核对/创建。按当前项目原生能力检查：

- 主图和流式归属、地图信息对象、客户端场景 ID/包名/配置名及显示名。
- 导航范围、可走/障碍网格、Pylon 与范围绑定。项目单图导出的 Pylon 数量约束不是 UE3 通则。
- Lightmass 范围、静态/动态灯光、烘焙设置及 Swarm 是否可连接。
- 目标坐标格、高差和导出边界。若确需整体平移，保留所有结构的相对关系，随后重新导出受影响数据；不要照搬历史地图的偏移值。

现有 MCP 缺能力时报告缺口；接口开发和集中编译需用户授权。不能拿无法查询的范围猜成已配置，也不能为补接口自行丢弃用户修改。发布前置能力应调用原生逻辑，而非手写替代 PHX/NAV/SCN。

## 5. 灯光完成看实际编码结果

队列已接受、Swarm 有进度、构建窗口结束、地图可保存都不是光照编码成功的充分证据。

- Swarm 连接失败与 Lightmass 导出/采样崩溃分开诊断。关掉提示不代表构建已恢复；先核对实际任务状态再有限重试。
- 线程断言保留真实线程边界；不能为继续烘焙屏蔽断言。涉及源码的根因和修复放在项目记录，普通地编 AI 遇到此类问题应暂停并反馈。
- 初次冷启动构建和同会话第二次构建行为不一致时，核对采集与导入是否采用同一初始化策略；重复成功不能替代冷启动验证。
- 核验本轮 mappings 导入、光照编码、光照贴图对象、未构建警告及明确保存完成。源包和 Cook 输出的光照贴图数量可能因系数裁剪不同，不按简单数量差直接判丢失。

## 6. 从零地图的发布与交付

按发布参考执行导航/Terrain、场景导出、增量索引登记、保存、隔离普通 Cook、文件清单与游戏验收。重点防止把旧图迁移中“没有新增依赖”的结论套到新创作：

- 项目 Cooker 可能保持新模型/材质/粒子 UPK 外部引用；显式 Cook 地图及实际新增资源，验证关键对象保留，不只交一份 UDK。
- 新建基础材质可能需要新增运行时 ShaderMap。即使 Cook 退出 0，仍要检查合并后的材质参考缓存是否进入发布清单；详见发布参考的缓存验收。
- 地图索引、GUID 和材质参考缓存各自以目标发布基线合并，不能互相替代，也不能用编辑器 Local 缓存覆盖运行缓存。
- 中间同名文件放到资源搜索范围外。缓存输出可能嵌在 Cook 会话的子目录；部署位置按运行消费者确认，不按输出目录形状原样复制。
- 交付列出相对路径、来源、哈希、客户端/服务端/参考各自职责，以及需要重新封包的目标。修改输入目录不代表实际 PAK 已更新。

完成记录分别包含：参考图结构落实、编辑器视觉、烘焙/导航语义、Cook/清单、用户真实入图，以及剩余行走/边界/重登/玩法项。用户说“能进游戏”仅关闭入图问题，不等于效果已百分之百符合参考图或整张地图玩法验收通过。
